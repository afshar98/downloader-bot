# Security and resource boundaries

## Input and provider

The bot accepts one bounded ASCII HTTP(S) URL token and validates the exact X/Twitter status URL
before admission. yt-dlp receives only the canonical status URL and metadata-only arguments, with
shell execution, config files, plugins, remote components, and arbitrary extractor selection off.
The provider process has bounded runtime and stdout/stderr; diagnostics never enter user responses
or logs.

## Media retrieval

SafeHttpClient requires HTTPS on the default port, rejects credentials and non-global IPv4/IPv6
answers, pins validated DNS results to the connection, and manually revalidates each redirect.
Responses must have an allowed status and media type and are streamed with identity encoding and a
byte counter. Redirect, timeout, and media-size limits are configured at startup. Deployment
network policy should also block private and internal destinations.

## Storage and resource limits

Each admitted request owns one uniquely created workspace below the configured existing, writable,
non-symlink `TEMP_DIR`. Filenames are generated by item position, writes are exclusive, partial files
are removed, and the workspace is recursively cleaned in a `finally` path. The default cap is 49
MiB per media item, two active jobs, and eight queued jobs. Do not place secrets or user-selected
paths in workspaces.

## Secrets and logs

Keep `TELEGRAM_BOT_TOKEN` in the deployment secret store or ignored local `.env`. Never print
environment values. Structured logs use opaque request IDs, stages, item positions, durations, and
stable error codes. Tokens, Telegram payloads, raw messages, URLs, headers, process output, paths,
filenames, and stack/cause data are redacted or omitted. Destination identifiers are not logged.
